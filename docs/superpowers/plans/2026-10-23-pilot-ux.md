# Pilot UX Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make the pilot status honest and clear, rebuild navigation as a collapsible sidebar plus account menu, add a participant/organiser profile with safe images, a draft privacy notice with real preference controls, honest dates and useful filters, and the reversed-gradient doodle background.

**Architecture:** Same single-page app at `/` (state-driven screens in `VisitorProvider`, `?e=` history for event detail) and `/admin`. Same anonymous Firebase auth. New public data lives in `profiles/{publicId}`, keyed by a random id that is never the uid, so a public profile cannot be joined to the uid-keyed `faces` initials. All permissions are enforced in `firestore.rules` and covered by `npm run test:rules`.

**Tech Stack:** React 19, TypeScript, Vite 6, Tailwind v4, motion/react, Firebase Auth (anonymous) + Firestore, vitest, Playwright (Chromium against the Firebase emulators).

**Spec:** the user's pilot-UX message of 2026-10-23 (sections 1–9 and the final handoff).

## Findings (what exists today)

- Routing: `/` (App) and `/admin` only. Screens are a `tab` state; event detail uses `?e=` + `history.pushState`, so the phone back button closes it.
- Sidebar: permanent 320px on ≥1024px, drawer on phones (Escape, tap outside, close button). Groups Me / Social / Discover / Create / Settings / Help / Admin, many "Coming soon" items that collect feature votes for /admin.
- Profile: private display name only (`users/{uid}.displayName`), initial avatar, "Only you see this profile". No images, no organiser profile.
- Organiser: "Help run this" panel (helper offer + earnings breakdown), Propose form (create-only `proposals`, admin-only read), "I have a space" (`venueOffers`). No organiser identity, drafts or own-proposal view. Venues collection exists but is not reachable from the public build.
- Images: `ImagePicker` + `compressToDataUrl` (JPEG data URL stored inside the Firestore document). No Firebase Storage in `firebase.json`; Storage for new projects needs the paid Blaze plan.
- Notifications: none sent by the app. Consents per purpose (`updates`, `organising`, `proposal`, `space`) with version + server timestamp; the founder contacts people by hand.
- Privacy: in-app note names the operator and an email, claims a 12-month retention that nothing implements. Self-service deletion removes contact details and initials only.
- Dates: seeding and proposal approval write made-up `deadline`/`startTime` (now + 21/28 days); cards show "Closes …". "This is happening" shows when interest reaches the target.
- Filters: category chips + search. City is hard-coded "Groningen". No date or location filter.
- Background: `body::before` navy→indigo→purple gradient, `body::after` two doodle SVG tiles at 20% opacity, strokes in fixed light purples.
- Tests: vitest (node, no DOM), rules + client-flow tests on the Firestore emulator. No component or browser tests.
- Missing references: none of the "previous design prompt" attachments are in this session; the brief above is the only source.

## Rulings

- Keep anonymous auth and "no login screen, ever" (CLAUDE.md). "Account & security" explains the device-bound account and offers deletion; one auth system serves both roles.
- Keep state-driven navigation; do not add a router. Back-button behaviour for `?e=` is preserved; the drawer closes on Escape/outside/selection.
- Images stay in Firestore as compressed data URLs (no Storage, no paid plan). Rules allow only `data:image/jpeg|webp;base64,` strings under fixed sizes; SVG is refused.
- Public profiles use a random `publicId` claimed through a write-only `profileOwners/{publicId}` document; the uid never appears in public data.
- New personal-data collection that the draft privacy notice cannot yet cover (public profile text/photos, organiser identity, launch/invitation emails) is built but switched off until `VITE_PRIVACY_NOTICE_FINAL=true`. Saved events, timing preference and Attend/Organise choice are private, pseudonymous and covered by the draft notice, so they ship on.
- Launch news and invitations go by email only, never WhatsApp/SMS. Delivery is manual; the UI never claims automatic email or unsubscribe links.
- Dates show only when an admin marks an event `dateConfirmed` and it is `Confirmed`. Existing `deadline`/`startTime` values are kept in the data but not shown.
- Location: events without a `city` count as the pilot city (Groningen). "Near" = same city or a listed city within 40 km by straight line. Browser geolocation only on a button press, rounded to the nearest listed city, coordinates never stored.
- Timing is a personal preference input (`users.preferredTiming`), labelled as such and summarised for admins; there is no timing data on events to filter by.
